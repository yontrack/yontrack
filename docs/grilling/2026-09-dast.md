Outcome of the grilling session of 2026-09-13 on automated penetration testing of Yontrack.

secrets) as its **DAST track**. All issues are of type **Task**. The `yontrack/yontrack` ones carry

## Where we start from

- **No DAST at all.** Supply chain (Trivy, Dependabot), SAST (CodeQL) and secrets are already
  covered or planned by #1747–#1754; nothing pentest-shaped existed.
- Customers **self-host** Yontrack (image + `yontrack-chart`): the scans protect the release,
  not a SaaS deployment.
- The public demo `https://demo.dev.yontrack.com` runs the latest BRONZE build of `main`, is reset
  and seeded by `demo-smoke.yml` (which gates SILVER), and its ingress exposes only the UI,
  `/graphql` and `/hook`.
- A full stack (backend, UI, Keycloak) already comes up on the runner in the `kdsl` and `ui-tests`
  jobs of `ci.yml`.
- Roles reach an OIDC user only through groups: IdP group → group mapping → Yontrack group →
  global / project roles, all declarable in CasC. The demo's CasC is empty, the chart's realm can
  only provision the admin, and the demo seed deletes and recreates every project.
- The repository is **public**: workflow logs and artifacts are readable by any signed-in user.
- Access-control bugs have been found by hand recently: #1739, #1741, #1742.

## Decisions

### Scope

- **DAST only**: scanning a running Yontrack over HTTP. Supply chain and SAST stay with the rest
  of the initiative.
- **Free tooling to start**: OWASP ZAP (Automation Framework, GraphQL add-on, Access Control
  Testing), graphql-cop, Nuclei.
- **Report only**: nothing blocks a build or a promotion.

Out of scope: dependency and image scanning, SAST, secret scanning (all elsewhere in the
initiative), commercial scanners, **authenticated crawling of the UI** (the UI goes through the
same API, which is scanned authenticated), **scanning released versions** (a finding on a release
is also on `main` unless already fixed; a patch is decided at triage), **creating GitHub issues
for findings**, and a manual run expected before GOLD.

### Two scans, two targets

| | Passive | Active |
|---|---|---|
| What | ZAP baseline, graphql-cop, Nuclei (no intrusive / DoS / fuzz templates) | ZAP full scan, GraphQL queries **and mutations**, access-control rules |
| Target | the demo instance — real ingress, TLS, Keycloak, chart defaults | a throwaway stack on the runner, seeded with `ontrack-demo-seed` |
| Why there | writes no data, tests the real deployment | creates, changes and deletes data |
| When | after each successful `demo-smoke`, weekly, on demand | weekly, on demand; 3-hour cap |
| Stamp | `SECURITY.DAST` on the deployed build | `SECURITY.DAST.ACTIVE` on the scanned BRONZE build |
| UI | unauthenticated: `/`, login redirect, `/api/auth/*`, `/api/health`, `/mobile` | — |

- The passive scan and `demo-smoke.yml` share the concurrency group `demo-instance`, so a reset
  never happens under a running scan.
- The passive scan ships first authenticated as the existing demo admin (`DEMO_TOKEN`); the three
  scanner roles follow (G).

### Scanner roles

Canonical declaration in `security/dast/casc.yaml`; the demo's gitops CasC is a copy pointing back.

| Keycloak user | Keycloak group | Yontrack group | Role |
|---|---|---|---|
| `scan-admin` | `dast-admin` | `DAST Admin` | global `ADMINISTRATOR` |
| `scan-readonly` | `dast-readonly` | `DAST Read-only` | global `READ_ONLY` |
| `scan-project` | `dast-project` | `DAST Project` | `PARTICIPANT` on one seeded project |

- On the demo: users from new `yontrack-chart` values `auth.keycloak.settings.users[]` /
  `groups[]`, passwords from secrets (H, I).
- On the throwaway stack: the same users in `compose/keycloak/import/oidc/ontrack.json` (E).
- `scan-project` loses its project on every demo reset; the CasC is re-applied after seeding by a
  remote reload, or failing that a new `grantProjectRoleToAccountGroup` mutation (F).
- Tokens by Keycloak password grant (the client allows it), sent as `Authorization: Bearer`.

### Findings: counting, reporting, disclosure

- **`security/dast/`** holds the ZAP plans, per-rule levels (`IGNORE`/`WARN`/`FAIL`),
  `suppressions.yaml` (rule, URL pattern, `statement`, `expired_at` — reviewed in git), the
  `rule → Yontrack mitigation` map `mitigations.yaml`, and the Nuclei template selection.
- **Counting** after suppressions: ZAP High/Medium/Low → HIGH/MEDIUM/LOW, Informational dropped;
  Nuclei one-to-one, including CRITICAL.
- **Stamps** are CHML, in no promotion: WARNING at MEDIUM ≥ 1, FAILED at HIGH ≥ 1.
- **Mitigation tracks**: a markdown report per run grouping findings by rule with their
  Yontrack-specific mitigation from the map. A Claude step writing mitigations is a later option,
  once the finding set is stable.
- **Disclosure**: logs show counts only, no workflow artifacts; the report is pushed to the
  **private** repository `yontrack/security-reports` (B). SARIF is uploaded to code scanning per
  tool (`dast-zap`, `dast-graphql`, `dast-nuclei`, `dast-zap-active`) — only if GitHub accepts
  and usefully renders URL-located findings; otherwise dropped, and the private report is the
  source of truth.
- A `SECURITY.md` and private vulnerability reporting come with it (A).

### Known findings

Decided before the first scan, so the first report is not mostly expected noise. The fixes are
blocked by C, so a report shows each finding before it is fixed and gone after.

| Finding | Decision | Issue |
|---|---|---|
| No security headers on the UI | **Fix** — `headers()` in `next.config.js`; CSP report-only first; HSTS left to the ingress | J |
| CORS `allowed-origins: "*"` on GraphQL / REST / hooks | **Fix** — same-origin by default, configurable allowlist; minor release | K |
| GraphQL introspection enabled | **Accept** — the schema is public on GitHub and needed by the UI; suppressed with that statement | C |
| Actuator chain `permitAll` on 8800, `exposure: *`, `show-details: always` | **Fix defaults** (L, minor release) + **deployment responsibility**: the chart must never route 8800 (H) | L, H |

### Frequency

| Scan | Cadence | Rationale |
|---|---|---|
| Passive, demo | after every successful `demo-smoke` + weekly | every deployed build gets a stamp; the weekly run catches new ZAP rules and Nuclei templates in quiet weeks |
| Active, throwaway stack | weekly + `workflow_dispatch` | 1–4 hours; a regression lives at most 7 days on `main` |

### Definition of done

- **Demo**: no demo content for any issue — this is CI tooling. The demo is a scan *target*; the
  seed is reused as scan data and its reset flow gains a CasC re-apply (F).
- **Mobile**: `/mobile` is part of the passive unauthenticated UI scan; the header fix (J) applies
  to it automatically and must be checked there; no mobile code change.
