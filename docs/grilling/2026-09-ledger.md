# The portable ledger and its import — Yontrack 6.1

Outcome of the grilling session of 2026-09-16 on block 2 of the delivery-harvesting brief
([2026-09-harvesting-brief.md](2026-09-harvesting-brief.md)): the ledger contract Yontrack owns,
and the extension that imports one. Ships in **6.1**.

Block 1, the harvester that produces a ledger inside an organization, was opened in this session
and deferred to its own; the three questions it reached are recorded at the end, unanswered, so the
next session starts from them rather than from zero.

The session settled 33 questions. This document records the decisions and the reasons, not the
questions. The issue breakdown comes in a following session and will be `2026-09-ledger-issues.md`,
under a new `initiative: ledger` label and a `6.1` milestone that does not exist yet and is created
when the issues are cut.

## Where we start from

Code facts checked during the session, beyond those already in the brief.

- **CasC upload is the precedent, and only half of one.** `POST /extension/casc/upload` takes a
  multipart file, is gated by a configuration property that defaults to off plus `GlobalSettings`,
  applies the file synchronously in the request thread, and has no dry run. Its JSON schema is
  published twice: through the generic `JsonSchemaProvider` registry that feeds the Resources page
  and `GET /rest/ref/schema/json/{key}`, and through a second CasC-specific URL.
- **There is no quiet mode.** `EventPostService` has one method, `post(event)`, with no
  suppression hook; `StructureServiceImpl` posts unconditionally on build, promotion run and
  validation run creation. `PromotionRunCheckService` runs every `PromotionRunCheckExtension` on
  every promotion run and has no bypass.
- **No import-style global function exists.** Bulk writes today are guarded by `GlobalSettings`
  (CasC) and `ValidationStampBulkUpdate`; everything else is per-project functions.
- **No external-id property exists** on builds or runs. The generic key/value carrier is
  `MetaInfoProperty`, searchable as `category/name:value`.
- **GitHub ingestion does not use the queue extension.** It has its own AMQP topic, its own
  routing and its own sync fallback for tests. The generic `QueueProcessor`, with routing
  identifier and sync-when-async-off, is what TFC, notifications, workflows and auto-versioning
  use.
- **Slot pipeline start is immutable**: a `val` defaulting to now, carried through every copy
  helper, and the repository's update writes only `END` and `STATUS`. `startPipeline` rejects
  ineligible builds, cancels every active pipeline, and `forceDone` is a parameter of it, not a
  separate path.
- The `yontrack` CLI is a Go binary in its own repository, `yontrack/yontrack-cli`, authenticating
  with a named configuration holding a URL and an API token.
- The validation data type alias for test summaries is `tests`, not `test-summary`; aliases are
  what `.yontrack/ci.yaml` and the CI-config JSON schema use.

## Decisions

### Shape and home

- **Ships in 6.1, as one extension, licensed.** `ontrack-extension-ledger` holds the schema, the
  upload endpoint, the queue processor, the fact handlers, the import records and the purge. 6.0
  is already the removal, the finding model, the delivery family and test stability; nothing in
  6.0 reads a ledger yet, and the changes the importer needs in `StructureServiceImpl` and the
  environments repository want their own review. No groundwork ships early: plumbing nobody uses
  for a release is how modules die.
- **The import is not the scorecard's feeder and not core.** Both the demo seed and Yontrack's own
  CI will produce ledgers, and neither should depend on the scorecard. The extension does not live
  in `ontrack-service` either: it has its own contract, audit trail and docs page.
- **Licensed feature "Ledger import"**, gated the way environments is: upload, dry run, the import
  records and the purge. The JSON schema stays downloadable without a license, because a contract
  that cannot be read is not one. No `enabled` configuration property on top, unlike CasC upload:
  CasC's property exists because CasC can rewrite security configuration; the ledger writes
  history under a global function and a license, which is enough.
- **A new global function, `LedgerImport`**, granted to Administrator and Automation, guards the
  door. Every fact then passes the per-entity checks of the service it calls, so an automation
  token that cannot edit project P cannot backfill P. Import is a privilege because it can write
  dates.
- **The async run executes as the uploader.** The upload captures the account, and the queue
  processor applies each fact as that account, the way workflows and auto-versioning carry their
  trigger. Running `asAdmin` like CasC would make the per-entity checks decoration.

### Vocabulary

Three words, each to get a `CONTEXT.md` entry with its _Avoid_ list before implementation starts.

- **Ledger**: an append-only, versioned file of delivery facts with provenance, produced outside
  Yontrack and replayed into it. History-as-code, as CasC is configuration-as-code. _Avoid_:
  bundle (the transport), snapshot (implies a state), ingestion (the GitHub hook framework's word),
  event (the notification system's).
- **Fact**: one entry of a ledger: one thing that happened, at one time, with an id, a basis and
  its evidence. _Avoid_: event, record (recordings), entry.
- **Import run**: one application of one ledger to one instance, with its status, counts and
  errors. _Avoid_: job (the job framework), load (CasC's word).

Producer-side words, for the next session: collector (reads a source), shipper (moves a ledger),
harvester (the whole producer).

### The ledger

- **A stream of facts, not a snapshot.** Each fact is one thing that happened, applied in order.
  Facts give an idempotency key per entry, make provenance trivially answerable, and are what a
  collector reading a pruned CI naturally produces. A state snapshot needs a diff engine and
  cannot represent a scan that later stopped reporting a finding.
- **Format: JSON Lines**, gzip accepted. A header line, then one fact per line, so a producer can
  stream and the importer never holds a ledger in memory. CasC is read by humans; a ledger is not.
- **Header**: `schemaVersion` (a single integer), `producer` (name and version), `source` (the
  organization or system harvested), `createdAt`. **Envelope** of a fact: `id`, `kind`, `time`,
  `basis`, `evidence`, `payload`.
- **Schema version is one integer.** The importer accepts every version up to its own and
  converts; a breaking change bumps the integer and lands in a 6.x minor at most, never a patch.
  One integer is enough for a format with one owner, and it is what the import run records.
- **The dedupe key is `(source, id)`.** Fact ids are strings unique within a source; producers are
  told to derive them deterministically from the natural key (a UUIDv5, or a readable
  `jenkins:job/42:promotion:GOLD`) so re-collecting yields the same ids and dedupe holds across
  ledgers. Two organizations harvested into one instance will both have a `build:1`. Builds still
  dedupe by name on top, through `createBuildOrGet`.
- **Time is required on every fact**, ISO-8601 with offset. The build's signature time is the
  fact's time; its signature user is the producer.
- **Basis is `MEASURED | ESTIMATED`**, with `evidence` free text or a URL. This is the slot the
  brief's "explicitly estimated fact with confidence and evidence" lands in, and what the
  scorecard's `basis = ESTIMATED` reads.
- **Fact kinds, closed for v1**: `project`, `branch`, `promotionLevel`, `validationStamp`,
  `environment`, `slot`, `build`, `promotion`, `validation`, `runInfo`, `link`, `deployment`,
  `property`. A stamp declaration carries an optional data type alias and config, because a
  `security-findings` run needs its thresholds on the stamp; level and stamp facts are optional,
  the importer still `getOrCreate`s from a bare reference. Environments and slots must pre-exist
  or be declared by their own fact, because slot admission rules are policy. Absent on purpose:
  subscriptions, workflows, auto-promotion rules, SCM configuration, admission rules. Every one is
  policy and goes through CasC.
- **A validation fact asserts one terminal status** with its time, plus optional typed data
  addressed by the data type **alias** (`tests`, `chml`, `security-findings`, `metrics`) and parsed
  through the type's `fromClient`. Status history cannot be backdated and nobody reads it in
  aggregate. Aliases rather than FQCNs, because the alias is what `.yontrack/ci.yaml` already uses
  and the FQCN is a Java detail no Go producer should know. This is how a scan enters: the door
  the scorecard session opened, not a second one.
- **Property facts carry an allow-list**: on builds `release`, `git commit` and `meta-info`; on
  branches `git branch`. Project SCM configuration is excluded: it names a named configuration and
  is policy. Meta-info is the deliberate escape hatch, where a producer puts the external ids it
  needs to find its way back, and it is searchable already.
- **A deployment fact** is a slot, a build, a start, an end and a terminal status.
- **No corrections in v1.** Facts are append-only; a wrong fact is fixed by purging the source and
  re-importing, or by hand. Retracting a build cascades through links, runs and pipelines and is a
  delete path with its own hazards; the fact table makes it addable later without changing the
  format.

### The import

- **Order is the importer's job within a ledger, and nobody's across ledgers.** The importer sorts
  facts by time per project before applying, ties broken by file order. A later ledger may carry
  older facts: that is exactly what "snapshot perishable sources early, reconstruct durable ones
  later" produces, so out-of-order across ledgers must be harmless, which the two decisions below
  make true.
- **Import writes below the promotion checks.** A backfilled promotion is recorded whether or not
  the dependency and previous-promotion conditions hold today. The checks are policy about what
  may be promoted next; a check configured in 2026 has nothing to say about 2024.
- **Quiet import: events are suppressed, side effects are not.** Years of history posted as events
  is the failure that gets the initiative banned. One exception: the importer posts a single
  `ledger_imported` event per run (source, counts, span) so a notification can say "history
  arrived". Findings rows, metrics, run info are still written: quiet suppresses events, not model.
- **One import context, three effects.** A thread-bound context set by the importer around each
  fact, consulted by `StructureServiceImpl` and the environments service, with exactly these
  effects: no event posting; the given signature is kept instead of `currentSignature`; promotion
  checks are skipped. One switch, documented and testable in isolation, rather than three flags on
  every service signature or a parallel raw-write service that re-implements validation.
- **What quiet breaks, and what repairs it.** Search indexing is event-driven, so imported builds
  are not searchable until the import run ends with a **re-index of the projects it touched**,
  which the indexation job already knows how to do. Auto-promotion, auto-versioning and slot
  workflows not firing is correct, not a gap: those are reactions to the present, and the ledger
  carries promotions as facts.
- **Model side effects must not ride on events — a constraint handed to block 3.** Writing
  findings and observations when a `security-findings` run lands is an inline part of the
  validation data type handling, never an `EventListener`, or imported scans would create no
  findings. The dividing line is the brief's: events drive reactions to the present; the model is
  written by the service call. To be recorded in the scorecard issues.
- **Backdating inventory, closed.** Build signature: kept by the import context. Promotion run
  time and validation run terminal status time: already settable. Run info creation time: stays
  now, `runTime` is what matters. Pipeline start and end: a new **record path** on `SlotService`
  that writes a pipeline row with the given start, end and status, one `SlotPipelineChange` row
  with the given time, and skips cancel-actives, admission rules and workflows. Admission rules
  describe what may deploy next, not what did deploy in 2024, and the pipeline table is where
  `delivery.leadTime` and `delivery.mttr` read from; history that lands anywhere else is invisible
  to the scorecard. Project and branch creation times stay now: no reading uses them.
- **Build links defer.** A link whose target is not in the instance yet is held to the end of the
  ledger and is an error if still unresolved. No placeholder builds: they would be phantom
  history. No immediate failure: it would make producers order across projects, which nothing
  else demands.
- **Upload validates synchronously and applies asynchronously.** `POST /extension/ledger/upload`
  parses and schema-validates the whole file in the request, rejects a malformed ledger with a
  4xx, persists the accepted facts, returns the import run id, and applies the facts through the
  queue extension's `QueueProcessor` with the project as routing identifier so per-project order
  holds. Sync when async is off, which gives deterministic tests. The raw file is not kept: the
  facts are the record. Schema errors surface at the door where the producer is standing; slow
  application runs behind.
- **Dry run is first-class**, a `dryRun` parameter on the upload and the CLI: full validation,
  reference resolution, and the counts of what would be created, skipped as already applied, and
  rejected, nothing written. "Nothing to inspect when numbers look wrong" was why the push gateway
  was rejected; dry run is the inspection. It is synchronous and bound by the same cap as upload.
- **A failing fact does not fail the run.** It is recorded with its error, its dependants in the
  same build are skipped, the rest continues, and the run ends `PARTIAL`. The fact table says
  which one failed so a producer fixes and re-ships only that.
- **Limits**: a settings entry with `maxFactsPerBundle`, default in the tens of thousands, plus
  the multipart size limit Spring already enforces. Dry run is the one path that must answer in
  the request, and a cap is what keeps a bulk endpoint from being a denial-of-service vector.

### Storage

- **A fact table** in `ontrack-database`: import run, source, fact id, kind, time, basis,
  evidence, status, error, and a reference to the entity the fact created. It is at once the
  dedupe index, the provenance the reading engine joins on to decide a reading's basis, and the
  answer to "which import created this". Provenance a metric cannot see is a comment; a property
  per entity would clutter every page and cannot be aggregated.
- **Fact rows cascade with their entity.** A build purged by retention takes its fact rows with
  it, and re-shipping the ledger recreates the build. Retention deleted it, a re-import is an
  explicit act, and the import run record still tells the story. Keeping rows with a nullable
  entity reference would make the fact table the one place in Yontrack that remembers deleted
  entities, which recordings do not do either.
- **Import runs are a `RecordingsExtension`**: status, counts, errors, source, span, with storage,
  GraphQL, cleanup and a records page for free.
- **No server-side watermark.** The collector must work disconnected, so it keeps its own; a
  server-side one would be a second source of truth, right only when the link is up.

### Labels and reset

- **Every project the importer creates or touches gets the label `ledger:<source>`**, the source
  from the header. The label is also the estate selection mechanism, so an imported organization
  is an estate the moment it lands.
- **`purgeLedgerSource(source)`**, admin-only, deletes the projects carrying that label plus the
  import runs and fact rows for the source. Purging by fact table, entity by entity, is the
  precise version but a mixed project, live builds beside imported ones, is exactly where a purge
  should be deliberate; it stays out of v1.

### API

- REST: `POST /extension/ledger/upload`, multipart, `dryRun` parameter, returns the import run id
  or the dry-run report.
- GraphQL: the recordings-provided `ledgerImportRuns` and record fields, `ledgerImportRun(id)`, the
  fact table queryable per run (status, error, entity), `purgeLedgerSource`.
- KDSL: upload and run polling, so acceptance tests can drive it.
- CasC: nothing beyond the settings entry.
- The schema is published through `JsonSchemaProvider` under key `ledger`, beside `ci-config` and
  `auto-versioning`, at `/rest/ref/schema/json/ledger` and on the Resources page. One route only:
  a second alias is how CasC ended up with two URLs for one schema.
- CLI, in `yontrack/yontrack-cli`: `yontrack ledger import <file> [--dry-run]` and
  `yontrack ledger validate <file>` for an offline schema check. Upload is the dumb-transport
  promise made good; the CLI is the USB-key path. A pull shipper (Yontrack fetching from a URL or
  bucket) is a later shipper, not v1.

### UI

- The records page from `RecordingsExtension`.
- A **"Ledger" user-menu item**: upload form, dry-run report, link to the schema.
- A **decoration on imported builds** through `DecorationExtension`, read from the fact table:
  the ledger icon, tooltip with source and basis. It is the only place a user sees "this build is
  history, not a run", which the estate view's measured-only toggle then reflects at scale.
- **No mobile impact**: the mobile UI reads builds and promotions, and an imported build is a
  build. Stated, not silent.

### Definition of done

- **Two producers validate the contract before block 2 is done**: `DemoTarget` re-expressed as
  "read a ledger, apply it", as a test in `ontrack-demo-seed`; and Yontrack's own CI emitting a
  ledger of its own builds. A contract only one producer has written is a private format. A real
  organization harvest is block 1's definition of done, not block 2's.
- **The demo shows it.** `DemoContent` ships a small ledger: a "harvested" legacy project with a
  few months of backdated builds, promotions, test runs and one deployment, imported through the
  extension under its own source label, so the demo shows an import record, the decoration, and a
  project whose readings are partly `ESTIMATED`. It is the cheapest end-to-end proof of the
  format, and the demo is where `ESTIMATED` first becomes visible.
- **Docs**: one mkdocs page, "Ledger import", under an integrations section: the format by
  pointing at the schema, the header, the dedupe and ordering rules, quiet mode and what it does
  not replay, purge, limits. `CONTEXT.md` entries for ledger, fact and import run.

## What this hands to block 3 and 4

- The constraint above: findings are written inline by the validation data type handling, never
  by an event listener.
- The fact table is what the reading engine joins to set `basis = ESTIMATED` and `unknownReason`.
- `ledger:<source>` labels are ready-made estate selectors.

## Block 1, opened and deferred

Three questions were put and not answered; the next session starts from them. The recommendations
below are the ones made in this session and carry no more weight than that.

1. **Repo layout.** The `yontrack` CLI is Go, so the harvester is Go. Recommended: a separate
   `yontrack-harvester` binary in the CLI's repository, sharing a ledger package with it, with
   `import` and `validate` in the CLI and `collect` and the mapping engine in the harvester.
   Collectors drag in Jenkins, Bitbucket, GitHub and spreadsheet clients that the binary every CI
   job downloads should not carry. Types generated from the published schema, pinned by a schema
   fixture in the repo.
2. **First collectors.** Recommended: git (tags, commits, branches) and GitHub Actions first,
   because together they produce Yontrack's own ledger, the second producer above; then Jenkins
   and Bitbucket for the target organization. Spreadsheets and other human sources are agent-mined
   into estimated facts, not a collector.
3. **Mapping configuration.** Recommended: one YAML file per organization in the organization's
   own harvest repository, declaring sources, project and branch naming rules, stamp and level
   mappings, and the deployment marker per source; validated against a JSON schema the harvester
   publishes. The mapping is the artifact an agent produces and a human reviews, so it must be
   diffable and re-runnable without a build. The ledger stays mapping-free so a producer with no
   mapping at all, Yontrack's CI, writes the same format.

Still untouched for block 1: source durability scheduling, the agent's exact role and review
loop, the shipper set, the harvest repo's own layout, and the watermark the collector keeps.
